# Decisions log

Decisions made while building Cutline where the spec (`SPEC.md`) left the choice open. Newest at the bottom.

## M0

- **Build tool: `electron-vite`.** Wraps Vite for all three processes (main/preload/renderer) with sane defaults for Electron's multi-process model, matches the spec's "Electron + Vite" stack directly, and its config maps cleanly onto the spec's `/src/main`, `/src/preload`, `/src/renderer` layout.
- **`vite@^7` + `@vitejs/plugin-react@^5`**, pinned explicitly. The versions that installed by default (`vite@8`, `@vitejs/plugin-react@6`) have peer-dependency ranges that don't yet agree with `electron-vite@5`. Pinned to the latest mutually-compatible majors.
- **State management: Zustand**, per the spec's own preferred default (over Redux Toolkit).
- **Styling: CSS Modules**, per the spec's own listed default (over Tailwind) — zero extra tooling, works out of the box with Vite.
- **FFmpeg build: `ffmpeg-static` (npm) — the gyan.dev GPLv3 Windows build.** It bundles `libx264`/`libx265`, hardware encoders (NVENC/QSV/AMF), and `vidstab` (needed later for M4 stabilization), all of which require the GPL build per the spec's own open decision in section 11. `ffprobe-static` ships the matching `ffprobe.exe` prebuilt (no network needed at install time, unlike `ffmpeg-static` which downloads from a GitHub release). License notice recorded in `THIRD_PARTY_LICENSES.txt` and surfaced from the About dialog, per section 9.
- **FFmpeg/FFprobe path resolution:** dev resolves `node_modules/ffmpeg-static/ffmpeg.exe` and `node_modules/ffprobe-static/bin/win32/x64/ffprobe.exe` directly (hardcoded relative paths, not `require()`-ing the packages) to avoid the bundler trying to statically bundle large binaries. Packaged builds resolve via `process.resourcesPath` against `extraResources` entries in `electron-builder.yml`, exactly as section 9 specifies. Both paths are exercised by the About dialog (dev via `npm run dev`, packaged via the built exe) — no automated test covers the packaged path yet since that requires a full `build:exe` run; the M0 acceptance criterion ("verified by launching the packaged build") covers this manually instead.
- **Window icon / taskbar icon:** generated programmatically (`scripts/generate-icon.mjs`, pure Node + zlib, no network/design-tool dependency) — a flat accent-blue rounded square with a white play triangle. Placeholder art; can be swapped for real design in M7 polish without any code change (same `resources/icon.ico` / `icon.png` paths).
- **No native OS menu bar.** `Menu.setApplicationMenu(null)` — the app's own UI (title bar + panels) is the whole interface, consistent with the "closer to CapCut... than a full broadcast suite" feel from section 1. Revisit if M7 wants a File/Edit/View menu for discoverability.
- **CSP applied via `session.defaultSession.webRequest.onHeadersReceived`** rather than a `<meta>` tag in `index.html`, so it can differ between dev (must allow the Vite dev server's HTTP/WS origin for HMR) and packaged (strict `default-src 'self'`) without shipping two HTML files.
- **`sandbox: true`** on the renderer's `webPreferences`, in addition to the spec-mandated `contextIsolation: true` / `nodeIntegration: false`. The preload script only needs `ipcRenderer`/`contextBridge`, so the extra isolation costs nothing.
- **`ELECTRON_RUN_AS_NODE` must be cleared before launching Electron in this dev environment.** The sandboxed shell this project is built in inherits `ELECTRON_RUN_AS_NODE=1` from its own (Electron-based) host tooling. Any Electron process launched with that variable set runs as plain Node instead of booting the normal app/window lifecycle, which — combined with an unrelated, still-open upstream bug (Electron 30+ rejects the `--remote-debugging-port=0` CLI flag Playwright injects, see [microsoft/playwright#39008](https://github.com/microsoft/playwright/issues/39008) / [#39922](https://github.com/microsoft/playwright/issues/39922)) — made `electron.launch()` fail outright. Fix: `Remove-Item Env:\ELECTRON_RUN_AS_NODE` (PowerShell) before `npm run dev`, `npm run test:e2e`, or launching a built exe from this shell. Not expected to affect real end users double-clicking the packaged exe from Explorer — only affects Electron-hosted dev/CI shells.
- **Known limitation to revisit in M1: `ffmpeg-static` and `ffprobe-static` ship mismatched FFmpeg versions.** Verified from the packaged build's About screen: `ffmpeg.exe` reports `6.1.1-essentials_build-www.gyan.dev` (2023), but `ffprobe.exe` reports `4.0.2` (2018) — they're independently-maintained npm packages, not extracted from the same release archive. Both run fine for M0's purposes (proving the binaries execute from `extraResources`), but a 5-year-older `ffprobe` may misreport or fail to recognize codecs/containers `ffmpeg` itself supports, which matters once M1 starts using `ffprobe` output to drive import decisions (codec support, proxy generation triggers). Fix then: source `ffprobe.exe` from the same gyan.dev release as the bundled `ffmpeg.exe` (that build's `Programs:` list confirms it includes `ffprobe`) instead of relying on `ffprobe-static`'s separate, older binary.
- **Core module scope for M0:** only `src/core/time.ts` (tick/timecode conversion helpers) and `src/core/diagnostics.ts` (types shared between main and renderer for the About screen). The full project/clip/command model is explicitly M1 work per section 3 ("Command pattern... Build this in M1; do not retrofit") — M0 only needed _something_ real in `/src/core` to prove the pure-TS-package boundary and the Vitest harness, and tick/timecode math is required by the schema in section 4 regardless of when the rest of the model lands.
