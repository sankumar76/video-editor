# Decisions log

Decisions made while building Cutline where the spec (`SPEC.md`) left the choice open. Newest at the bottom.

## M1

- **Command history: whole-project snapshots, not hand-written inverses.** Every edit captures the full "before" and "after" `Project` value; `undo`/`redo` just swap between them (`src/core/commands/history.ts`). A project is a few KB of JSON even with hundreds of clips, so the memory cost is negligible, and it makes every edit's undo _correct by construction_ — no risk of a hand-written inverse (e.g. for ripple-delete or split) drifting from its forward operation. All edit functions in `src/core/commands/edits.ts` are therefore plain `(Project) => Project` functions with no paired undo logic to maintain.
- **Codec-support allowlist for the proxy decision** (`src/core/media/codecSupport.ts`): conservative container/codec allowlist (mp4/mov/m4v/webm/ogg containers; h264/vp8/vp9/av1 video; aac/mp3/opus/vorbis/flac audio). A false negative just costs an unnecessary proxy; a false positive means a silent black preview, so the allowlist errs conservative per spec section 2.
- **`ffmpeg-static`'s bundled `ffmpeg.exe` and `ffprobe-static`'s bundled `ffprobe.exe` are different FFmpeg builds/versions** (flagged in M0's decisions). Not fixed in M1 either — both still work correctly for probing/proxy/export — but noted again here since M1 is the milestone that actually depends on probe accuracy. Revisit if a real-world file's probe result looks wrong.
- **Preview audio: each active clip's own `<video>`/`<audio>` element plays directly** (respecting track mute/solo and clip volume), not a Web Audio mixing graph. The spec's architecture section mentions Web Audio for the general case, but real-time mixing/ducking/effects don't exist until M3 — until then a graph would add complexity with no behavioral difference over just setting `.volume`/`.muted` on the elements themselves. Revisit when M3 needs an actual mix graph (EQ, compressor, ducking).
- **Playback clock is wall-clock-driven, not derived from a "primary" element's `currentTime`.** `usePlaybackEngine` accumulates its own tick position from `requestAnimationFrame` deltas and re-seeks each active media element whenever it drifts more than ~120ms. Simpler to reason about with multiple simultaneous video tracks (no single element is "authoritative"), at the cost of small preview-only audio/video drift — acceptable since the spec's audio/video sync guarantee ("within 1 frame over 60 minutes") is an _export_ correctness requirement, not a preview one.
- **JKL shuttle is 1x-only, not variable-speed.** J/L play at normal speed in reverse/forward; repeated presses don't accelerate like a professional shuttle. True variable-speed reverse playback of compressed video is unreliable even in native players; a full implementation is deferred. Frame-step (arrow keys) and normal forward playback (native `.play()`, audio intact) are both fully accurate.
- **Dragging a clip on the timeline moves only that clip (+ its linked partner), not the whole multi-selection.** Group-drag of several independently-selected clips is a nicer interaction but adds real coordination complexity (per-clip collision checking against every other selected clip's proposed new position simultaneously); "select multiple" and "move a clip" are each independently satisfied without it. The architecture doesn't preclude adding it later.
- **Linked video+audio clip pairs stay in sync for move, trim, and split** — trimming one edge of either clip re-trims its partner to the same proposed edge time; splitting one splits its partner at the same point and re-links the resulting halves to each other. Deleting one does _not_ auto-delete or auto-unlink the other from a single clip id — callers (keyboard shortcuts, toolbar buttons) explicitly resolve `[clipId, ...linkedPartnerIds]` before calling delete, since "select one of a pair, ripple-delete just that one" is also a legitimate action once a project supports unlinking (a later milestone).
- **Track `locked` is enforced at the UI layer** (drag/trim pointer handlers no-op when `track.locked`), not inside the core edit functions themselves. The core functions stay simple, unconditional appliers; "is this edit allowed right now" is interaction policy, which belongs in the renderer.
- **Deleting a media item that's in use cascades to delete the clips referencing it** (after a confirmation prompt), rather than leaving a "missing media" placeholder clip. The spec's cross-cutting reliability section describes placeholder clips for _files that go missing on disk_ (relink workflow, M6) — that's a different scenario from _the user explicitly deleting media from the bin in the same session_, where cascading delete is the less surprising behavior and avoids building placeholder-clip rendering before M6 needs it anyway.
- **Real bug found via testing, not inspection: `app.getAppPath()` doesn't reliably resolve to the project root.** It differs depending on how the unpackaged main process is launched — `electron-vite dev` gets it right, but a direct `electron.exe out/main/index.js` invocation (which is how Playwright's `electron.launch()` starts the app, and how M0's own e2e test runs) resolves it to `out/main` instead. This silently broke dev-mode FFmpeg/FFprobe path resolution and would have broken the icon/license-file paths too; the M0 e2e test didn't catch it because its FFmpeg assertion only checked that the About dialog _finished loading_, not that the check actually succeeded (an error state also stops "loading"). Fixed by deriving the project root from `__dirname` instead (`src/main/devRoot.ts`) — deterministic regardless of launch method — and by strengthening the M0 About-dialog e2e assertion to require the literal version string, not just "not stuck loading."
- **Export's `-loop 1` handling for images:** `buildFilterGraph` flags each input as `isImage`; `runExport` adds `-loop 1` before that input's `-i` so a still image behaves like an indefinite-length video source, letting the exact same `trim`/`setpts` pipeline used for real video clips work unchanged for images. No image-specific branch needed in the filter-graph builder itself.
- **Recent-projects list** is a flat JSON array (path/name/last-opened) capped at 10 entries in `userData/recent-projects.json`, trimmed on write. Simple enough not to need a real database for v1.
- **Test fixtures generated with FFmpeg `testsrc`/`sine`, per spec section 10:** `tests/fixtures/` now has H.264, HEVC (proxy-triggering), VFR, audio-only, image, and portrait-rotated (rotation metadata) samples, all synthetic and small (no downloaded assets, fast to regenerate).

## M0

- **Build tool: `electron-vite`.** Wraps Vite for all three processes (main/preload/renderer) with sane defaults for Electron's multi-process model, matches the spec's "Electron + Vite" stack directly, and its config maps cleanly onto the spec's `/src/main`, `/src/preload`, `/src/renderer` layout.
- **`vite@^7` + `@vitejs/plugin-react@^5`**, pinned explicitly. The versions that installed by default (`vite@8`, `@vitejs/plugin-react@6`) have peer-dependency ranges that don't yet agree with `electron-vite@5`. Pinned to the latest mutually-compatible majors.
- **State management: Zustand**, per the spec's own preferred default (over Redux Toolkit).
- **Styling: CSS Modules**, per the spec's own listed default (over Tailwind) — zero extra tooling, works out of the box with Vite.
- **FFmpeg build: `ffmpeg-static` (npm) — the gyan.dev GPLv3 Windows build.** It bundles `libx264`/`libx265`, hardware encoders (NVENC/QSV/AMF), and `vidstab` (needed later for M4 stabilization), all of which require the GPL build per the spec's own open decision in section 11. `ffprobe-static` ships the matching `ffprobe.exe` prebuilt (no network needed at install time, unlike `ffmpeg-static` which downloads from a GitHub release). License notice recorded in `THIRD_PARTY_LICENSES.txt` and surfaced from the About dialog, per section 9.
- **FFmpeg/FFprobe path resolution:** dev resolves `node_modules/ffmpeg-static/ffmpeg.exe` and `node_modules/ffprobe-static/bin/win32/x64/ffprobe.exe` directly (hardcoded relative paths, not `require()`-ing the packages) to avoid the bundler trying to statically bundle large binaries. Packaged builds resolve via `process.resourcesPath` against `extraResources` entries in `electron-builder.yml`, exactly as section 9 specifies. Both paths are exercised by the About dialog (dev via `npm run dev`, packaged via the built exe) — no automated test covers the packaged path yet since that requires a full `build:exe` run; the M0 acceptance criterion ("verified by launching the packaged build") covers this manually instead.
- **Window icon / taskbar icon:** generated programmatically (`scripts/generate-icon.mjs`, pure Node + zlib, no network/design-tool dependency) — a flat accent-blue rounded square with a white play triangle. Placeholder art; can be swapped for real design in M7 polish without any code change (same `resources/icon.ico` / `icon.png` paths).
- **No native OS menu bar.** `Menu.setApplicationMenu(null)` — the app's own UI (title bar + panels) is the whole interface, consistent with the "closer to CapCut... than a full broadcast suite" feel from section 1. Revisit if M7 wants a File/Edit/View menu for discoverability.
- **CSP applied via `session.defaultSession.webRequest.onHeadersReceived`** rather than a `<meta>` tag in `index.html`, so it can differ between dev (must allow the Vite dev server's HTTP/WS origin for HMR) and packaged (strict `default-src 'self'`) without shipping two HTML files.
- **`sandbox: true`** on the renderer's `webPreferences`, in addition to the spec-mandated `contextIsolation: true` / `nodeIntegration: false`. The preload script only needs `ipcRenderer`/`contextBridge`, so the extra isolation costs nothing.
- **`ELECTRON_RUN_AS_NODE` must be cleared before launching Electron in this dev environment.** The sandboxed shell this project is built in inherits `ELECTRON_RUN_AS_NODE=1` from its own (Electron-based) host tooling. Any Electron process launched with that variable set runs as plain Node instead of booting the normal app/window lifecycle, which — combined with an unrelated, still-open upstream bug (Electron 30+ rejects the `--remote-debugging-port=0` CLI flag Playwright injects, see [microsoft/playwright#39008](https://github.com/microsoft/playwright/issues/39008) / [#39922](https://github.com/microsoft/playwright/issues/39922)) — made `electron.launch()` fail outright. Fix: `Remove-Item Env:\ELECTRON_RUN_AS_NODE` (PowerShell) before `npm run dev`, `npm run test:e2e`, or launching a built exe from this shell. Not expected to affect real end users double-clicking the packaged exe from Explorer — only affects Electron-hosted dev/CI shells.
- **Known limitation to revisit in M1: `ffmpeg-static` and `ffprobe-static` ship mismatched FFmpeg versions.** Verified from the packaged build's About screen: `ffmpeg.exe` reports `6.1.1-essentials_build-www.gyan.dev` (2023), but `ffprobe.exe` reports `4.0.2` (2018) — they're independently-maintained npm packages, not extracted from the same release archive. Both run fine for M0's purposes (proving the binaries execute from `extraResources`), but a 5-year-older `ffprobe` may misreport or fail to recognize codecs/containers `ffmpeg` itself supports, which matters once M1 starts using `ffprobe` output to drive import decisions (codec support, proxy generation triggers). Fix then: source `ffprobe.exe` from the same gyan.dev release as the bundled `ffmpeg.exe` (that build's `Programs:` list confirms it includes `ffprobe`) instead of relying on `ffprobe-static`'s separate, older binary.
- **Core module scope for M0:** only `src/core/time.ts` (tick/timecode conversion helpers) and `src/core/diagnostics.ts` (types shared between main and renderer for the About screen). The full project/clip/command model is explicitly M1 work per section 3 ("Command pattern... Build this in M1; do not retrofit") — M0 only needed _something_ real in `/src/core` to prove the pure-TS-package boundary and the Vitest harness, and tick/timecode math is required by the schema in section 4 regardless of when the rest of the model lands.
